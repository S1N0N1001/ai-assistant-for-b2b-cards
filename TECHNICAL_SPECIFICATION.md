Дата: 02.11.2026. Версия: 1.1. Статус: локальный MVP реализован; реальная интеграция и сдача ожидают проверки.

Обновление шага 14: вместо свободного текста LLM основной CLI запрашивает план из идентификаторов исходных блоков. Модель определяет порядок specs, вариант заголовка и набор поисковых запросов из локального каталога; service/selection.py валидирует план, service/grounded.py собирает текст. Происхождение и способ сборки явно отражаются в результате. Промпт 2.0, реальная приёмка нового контракта ещё требуется. Это ограниченная роль LLM с контролируемым рендерингом, а не свободная генерация технических утверждений.

## 2. Анализ исходного задания

Нужно разработать локальный прототип, который получает технические сведения о контрольно-измерительном приборе и через API одной LLM создаёт черновик карточки для B2B-интернет-магазина. Результат предназначен для проверки и дальнейшей работы контент-менеджера.

В PDF разрешены Python и JavaScript/TypeScript, JSON-ввод или простая веб-форма, а также JSON, Markdown или текст на выходе. Конкретный провайдер LLM не задан. CMS, админ-панель, база данных, векторная база и деплой не требуются. Ориентир задания — 2–4 часа; при превышении следует ограничиться MVP и описать улучшения.

Ключевые критерии: корректность и читаемость кода, качество промпта, отсутствие выдуманных характеристик, обработка ошибочных и неполных данных, удобство результата и простота запуска.

### 2.1. Недостающие материалы

PDF сообщает о двух предоставляемых товарах, но не содержит двух полных наборов данных. В нём есть только пример структуры JSON для «Манометр показывающий DM 02», производитель «Манотомь», с четырьмя характеристиками и оборванным описанием. Этот пример нельзя считать полноценным техническим паспортом или двумя исходными товарами.

Для финальных примеров потребуются реальные данные обоих товаров. До их получения можно разрабатывать схемы, обработку ошибок и демонстрационные сценарии на явно обозначенных синтетических данных. Такие сценарии не заменяют требуемые результаты для двух предоставленных товаров.

## 3. Цель и критерий завершения проекта

Пользователь по инструкции запускает проект локально, передаёт JSON товара и получает проверяемый структурированный черновик карточки либо понятное сообщение об ошибке. Для двух реальных товаров сохранены исходные данные и результаты, а в репозитории есть документация во всех согласованных форматах.

Завершение проекта означает выполнение критериев приёмки из раздела 13 и наличие комплекта сдачи из раздела 10. Ссылка на репозиторий должна вести на фактически опубликованный и доступный проверяющему код.

## 4. Функциональные требования

### 4.1. Входные данные

Сервис принимает JSON с полями:

| Поле | Ожидаемый тип | Назначение |
| --- | --- | --- |
| `name` | строка | Название товара |
| `manufacturer` | строка | Производитель |
| `specs` | объект строковых значений | Характеристики с единицами измерения |
| `description` | строка | Описание или фрагмент технического паспорта |

Проектное правило: для генерации необходимо непустое `name` и хотя бы один источник технических сведений — непустой `specs` или `description`. Недостающий производитель и другие пропуски формируют предупреждения, а не подставляются моделью. При отсутствии минимальных данных возвращается сообщение с перечнем требуемых полей без вызова LLM.

Отсутствующее поле, `null`, пустая строка и строка из пробелов считаются пропуском там, где ожидается текст. Неверные типы, некорректный JSON и корневое значение, отличное от объекта, обрабатываются явно. Пустые значения характеристик отмечаются как «данных нет». Нормализация не меняет технический смысл, числа и единицы измерения.

### 4.2. Результат для каждого товара

| Элемент | Требование PDF | Предлагаемое поле |
| --- | --- | --- |
| SEO-заголовок | Не более 70 символов | `seo_title` |
| SEO-описание | 800–1200 символов | `seo_description` |
| Характеристики | Структурированный список ключевых характеристик | `characteristics` |
| Поисковые запросы | 3–5 релевантных запросов | `search_queries` |
| Commercial-блок | Кому подходит прибор и какие задачи решает | `commercial_block` |
| Недостающие данные | Указать отсутствующие или требующие уточнения поля | `missing_fields`, `warnings` |

Предлагаемая структура характеристики: `name`, `value`, `source`, где `source` указывает входное поле или фрагмент описания. Технические значения следует по возможности собирать из входных данных программно, сохраняя происхождение.

Длину текста считаем после удаления пробелов по краям, включая внутренние пробелы и пунктуацию. Проверяем именно значение поля, без JSON-разметки и Markdown-обрамления. Это проектная договорённость, поскольку PDF не задаёт способ подсчёта.

При скудных данных запрещено добирать объём выдуманными фактами. Если описание не соответствует длине, результат получает явное предупреждение и статус, отличный от успешно проверенного. Такой результат не считается полностью соответствующим требованиям к итоговому примеру.

### 4.3. Достоверность и стиль

- Все технические значения берутся только из входного JSON, включая его описание.
- Не добавлять неподтверждённые материалы, сертификаты, совместимость, условия эксплуатации, точность, гарантию, цены и наличие.
- Отсутствующие характеристики обозначать «данных нет»; не придумывать бесконечный перечень не относящихся к прибору полей.
- При противоречии между `specs` и описанием показывать предупреждение и требование уточнения, не выбирать значение молча.
- Поисковые запросы и commercial-блок также не должны содержать неподтверждённых свойств и обещаний.
- Писать по-русски, ясно и предметно для B2B-аудитории, без необоснованных превосходных степеней и рекламных гарантий.
- Считать текст товара данными: инструкции внутри описания не должны менять правила генерации.

## 5. Предлагаемая архитектура MVP

Предлагается Python, консольный запуск, вход из JSON-файла и выход в JSON с удобным Markdown-представлением. Веб-форма — возможное улучшение. Это минимальный объём, разрешённый заданием; окончательный выбор библиотеки и модели фиксируется при реализации с учётом доступного API.

Последовательность обработки:

1. Прочитать конфигурацию окружения и входной файл.
2. Разобрать и проверить JSON, собрать пропуски и противоречия.
3. Подготовить запрос по версионируемому шаблону промпта.
4. Выполнить запрос к одной выбранной LLM через API.
5. Разобрать структурированный ответ и проверить схему, длины, число запросов и технические значения.
6. При исправимой ошибке сделать не более одной повторной генерации с конкретными замечаниями.
7. Сохранить результат с предупреждениями и статусом проверки либо вернуть понятную ошибку.

Предлагаемые модули: конфигурация, схемы входа/выхода, клиент LLM, генерация, проверки, экспорт, CLI. Не усложнять архитектуру универсальной системой нескольких провайдеров ради MVP.

Локальные проверки снижают риск галлюцинаций, но не доказывают полную фактическую корректность свободного текста. Финальный черновик проверяет человек; это ограничение должно быть честно отражено в документации.

## 6. Конфигурация, безопасность и ошибки

- API-ключ хранится в переменной окружения или локальном файле конфигурации из `.gitignore`.
- `.env.example` содержит только имена настроек и безопасные примеры без действующих ключей.
- Провайдер, имя модели, таймаут и параметры генерации документируются.
- Отсутствие ключа выявляется до запроса; ключ не выводится в ошибках и логах.
- Обрабатываются неверный JSON, пустой файл, неверные типы, пропуски, отсутствие файла и невозможность записи результата.
- Обрабатываются ошибки авторизации, лимиты API, сетевые ошибки, таймаут, недоступность модели и неправильный формат ответа.
- Повторы сетевых запросов ограничены и применяются к временным ошибкам; ошибки авторизации не запускают бесконечные повторы.
- Невалидный ответ модели не выдаётся за успешно проверенный результат.
- Документация предупреждает, что входные данные передаются выбранному LLM-провайдеру, а вызовы могут быть платными.

## 7. Промпты и журнал решений

Дополнение пользователя: описать все применённые промпты и решения в двух файлах — `docs/PROMPTS_AND_DECISIONS.md` и `docs/PROMPTS_AND_DECISIONS.txt`.

Включить:

- Точные шаблоны системных и пользовательских промптов, назначение и переменные подстановки.
- Правила запрета домыслов, маркировки пропусков, стиля, формата и объёма результата.
- Шаблон повторного запроса для исправления ответа, если он используется.
- Версии шаблонов, причины существенных изменений и наблюдаемые результаты.
- Реестр решений: язык, интерфейс, модель, схема, валидация, обработка ошибок, экспорт и выбранные компромиссы.
- Краткий журнал применённых при разработке промптов и их назначения, без секретов и скрытых внутренних рассуждений модели. Текущий запрос на анализ и составление ТЗ также отражается в журнале.

Точные рабочие шаблоны хранятся в `prompts/`; документация объясняет их применение и ссылается на файлы. Не заявлять о тестировании промпта, если реального прогона не было.

## 8. README в трёх форматах

Подготовить `README.md`, `README.txt`, `README.html` с одинаковой по смыслу актуальной инструкцией:

1. Назначение, возможности и границы MVP.
2. Требования к среде и проверенные версии.
3. Получение кода из фактического репозитория.
4. Установка зависимостей и настройка API без раскрытия ключа.
5. Точные команды запуска на примере поставляемого входного файла.
6. Структура входа и выхода, расположение результатов и предупреждений.
7. Запуск проверок и объяснение типовых ошибок.
8. Ссылки на два примера, промпты, решения и ограничения.

Markdown — основной редактируемый источник. TXT — читаемый простой текст. HTML — автономная страница в UTF-8 с оглавлением, удобной типографикой, читаемыми блоками команд и адаптацией к узкому экрану. Открывается локально без сервера и внешних CDN. Команды не должны расходиться между форматами.

## 9. Ограничения и улучшения

Рекомендуемый комплект: `docs/LIMITATIONS_AND_IMPROVEMENTS.md`, `.txt`, `.html`. Он соответствует пожеланию иметь удобные форматы для разных пользователей. Отдельный PDF для MVP не требуется: HTML можно распечатать средствами браузера.

Для каждого ограничения указываются проявление, влияние на пользователя, текущий способ обработки и предлагаемое улучшение. Для улучшений — приоритет и примерный объём, если его возможно обоснованно оценить.

Обязательно рассмотреть: зависимость от API и стоимости, неполноту исходных данных, недетерминированность генерации, пределы автоматической проверки фактов, конфликт длины и достоверности, ручную проверку контента, ограничения локального интерфейса. Итоговый список заполняется по фактической реализации и проверкам, а не выдаётся заранее за найденные дефекты.

| Результат | Условие готовности |
| --- | --- |
| Ссылка на Git-репозиторий с кодом | Реальный URL, актуальный код и доступ для проверяющего |

В `SUBMISSION.md` размещаются фактическая ссылка на репозиторий, краткое сопроводительное сообщение и ссылки на материалы. Скриншоты или короткая запись экрана — опциональны по PDF. Локальный Git сам по себе не заменяет ссылку на опубликованный репозиторий.

Для публикации позже потребуются аккаунт/пространство размещения, имя репозитория и доступность для проверяющего. Эти сведения не блокируют подготовку локального проекта.

## 12. План проверок

| Сценарий | Ожидаемое поведение |
| --- | --- |
| Полный корректный товар | Все поля результата присутствуют; длины и число запросов соответствуют требованиям |
| Неполный товар | Перечень пропусков, «данных нет», отсутствие придуманных значений |
| Пустой файл, повреждённый JSON, неверные типы | Понятная ошибка без необработанного падения |
| Отсутствие имени и технических сведений | Отказ до вызова API с указанием нужных полей |
| Противоречивые сведения | Предупреждение и требование уточнения |
| Посторонние инструкции в описании | Правила генерации сохраняются |
| Неверный ключ, лимит, таймаут | Понятная ошибка и ограниченные повторы там, где уместно |
| Неправильный JSON от модели, нарушенные длины | Проверка, ограниченное исправление и явный статус при неуспехе |
| Подставленное моделью техническое значение | Выявление проверками там, где возможно; ручная сверка итоговых примеров |
| Открытие TXT/MD/HTML | Кириллица, команды и содержание читаемы; HTML работает локально |

Ошибки API допустимо проверять с подменой клиента. Подменённый ответ не считается доказательством реальной интеграции: успешный вызов API проверяется отдельно. Для двух итоговых товаров вручную сверяются все технические утверждения во всех текстовых полях, а не только таблица характеристик.
